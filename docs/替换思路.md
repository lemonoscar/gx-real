# 替换思路

你的目标不是重写整套真机系统，而是：

- 机器人硬件仍然是 `Go2 + X5`
- 最底层执行链尽量复用 `umi-on-legs` 现有真机控制
- 你自己的网络系统替换掉他们原来的“任务输入 / 上层策略 / 甚至 whole-body policy”

这件事是可行的，而且最稳妥的做法不是从 `lowcmd` 或 CAN 层直接下手，而是先搞清楚这套系统的分层。

---

## 0. 最近真机部署后的理论修正

下面的修正来自当前 `Go2 + X5/ARX5 + Jetson + SpaceMouse` 真机上机链路，不是原 UMI-on-Legs 论文链路的抽象推演。

### 0.1 当前主线不是 18 维 whole-body 输出

当前仓库主线已经收敛成：

```text
Go2 腿部：
  260D observation -> policy.onnx -> 12D leg action -> Go2 lowcmd

X5/ARX5 机械臂：
  SpaceMouse raw input -> SpaceMouse Arm Node -> ARX5 can0 command

WBC：
  只写 Go2；
  只读 /arm/state 和 /arm/target_state；
  不默认打开 can0。
```

因此，后续谈“替换网络”时不能再默认是“替换 18 维 whole-body actor”。当前默认可替换对象是 `260D obs -> 12D leg action`；机械臂动作来自外部 SpaceMouse Arm 节点，WBC 只把机械臂状态和目标作为 observation 的一部分。

### 0.2 控制权必须按写入域划分

当前真机上最重要的边界不是“哪个节点订阅了什么 topic”，而是谁在写硬件：

```text
WBC Leg Node:
  唯一写 Go2 lowcmd
  不写 X5

SpaceMouse Arm Node:
  唯一写 X5 can0
  不写 Go2
```

这条边界解释了几个现象：

- Go2 手柄 `/wirelesscontroller` 的摇杆只应该改变底盘 command，不应该直接改变 X5。
- `A/B/X/D-pad` 在当前主线里是 no-op，不再是机械臂控制入口。
- WBC 使用 `--arm-control-owner external_spacemouse` 时，`--arm_pose` 只是 observation fallback，不会下发给机械臂。
- 不允许同时运行 ARX5 SDK 示例、legacy WBC arm writer 和 `scripts/run_spacemouse_arm.sh`。

### 0.3 前置脚本只负责证明“可运行”，运行命令才是可调层

真机流程已经拆成两类：

```text
前置封装：
  scripts/prepare_real_run.sh

真实运行：
  scripts/run_spacemouse_arm.sh
  scripts/run_leg12_real.sh
```

前置脚本负责编译消息包、检查 Python/type support、确认 CycloneDDS、检查 SpaceMouse、配置 `can0`、检查 Go2 topic、关闭 sport mode。它的目标是把“每次都应该一样”的工作封装掉。

运行命令才是允许调整的层，例如：

- `--joy-*` 摇杆轴、符号、速度上限和 deadzone。
- `--sm-*` SpaceMouse 坐标、速度和 watchdog。
- `--leg-kp/--leg-kd` 和 policy 相关参数。

如果前置脚本失败，不应该靠改运行命令绕过；应该先修环境、网络、CAN 或硬件链路。

### 0.4 ROS2/DDS 是上机链路的一等前提

当前 Go2 ROS2 通信必须使用 CycloneDDS，并绑定到连接 Go2 的网卡：

```text
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
GX_REAL_NETWORK_IFACE=eth0
CYCLONEDDS_URI=<... NetworkInterface name="eth0" ...>
```

如果 `run_spacemouse_arm.sh` 在打印 `Arm control owner...` 之前就出现 `std::bad_alloc` 一类错误，优先按 ROS2 middleware 初始化问题处理，而不是先怀疑 CAN 或 SpaceMouse。当前 `scripts/setup_env.sh` 会自动打印：

```text
[gx-real] rmw=rmw_cyclonedds_cpp
[gx-real] cyclonedds_iface=eth0
```

这两行是 runtime shell 是否进入正确 DDS 配置的直接证据。

### 0.5 SpaceMouse watchdog 不应该让机械臂掉下

早期实现里，SpaceMouse 样本 stale 后会进入 damping。这在机器狗开始走动时会放大 USB/CPU/daemon 抖动的影响：底盘一动，SpaceMouse reader 短暂 stale，机械臂就掉下来。

当前理论修正是：

```text
SpaceMouse 数据短暂 stale:
  hold current pose

真正急停 / 节点退出 / 控制错误:
  damping
```

所以判断机械臂“自己掉下来”时要先看日志：

- `SpaceMouse watchdog expired; holding X5 arm`：watchdog 触发，但应该保持当前位姿。
- `Emergency stop received ... damping X5 arm`：急停路径，damping 是预期。
- ARX5 SDK 初始化失败或进程退出：不是 SpaceMouse 映射问题，先查 CAN/硬件。

### 0.6 `can0 UP` 不等于 X5 可控

`ip -details -statistics link show can0` 只能证明 SocketCAN 接口存在并且有统计计数。它不能证明 ARX5 SDK 已经解析到正确电机状态。

ARX5 初始化真正需要的是：

```text
can0 打开成功；
X5 电机有供电并回包；
CAN-H/CAN-L/GND 正确；
bitrate 正确；
model 配置的 motor_id / motor_type 能解析这些回包。
```

如果日志是：

```text
None of the motors are initialized.
```

含义是 SDK 已经打开 `can0`，但初始化阶段读到的 6 个关节位置仍全为 0。此时按下面顺序判断：

1. 用 `candump -tz can0` 看启动瞬间是否有当前回包，而不是只看累计 RX/TX。
2. 如果只有 TX 或没有当前 RX，查 X5 供电、急停、CAN-H/CAN-L/GND、终端电阻和 USB-CAN 接线。
3. 如果有大量当前 RX，但 SDK 仍认为无电机，优先怀疑 `--model X5_umi` 与实际电机协议/ID 不匹配，可受控尝试 `--model L5_umi`。
4. `free(): invalid pointer` 是 ARX5 SDK 初始化失败后的清理崩溃，不是第一根因；第一根因仍是 `None of the motors are initialized`。

### 0.7 当前替换路线应重新排序

基于现在的真机主线，推荐顺序应改成：

1. 固定当前部署壳层：`prepare_real_run.sh` + 两个 runtime 终端。
2. 先把 `wireless_joystick` 底盘速度和 `SpaceMouse Arm` 机械臂控制跑稳。
3. 替换腿部 `12D policy.onnx` 时，保持 `260D obs` 契约和 `env.yaml` 同步。
4. 只有需要恢复原 UMI whole-body trajectory tracking 时，才重新讨论 `eef_state -> eef_traj -> 18D action` 这条历史链路。

换句话说，当前最稳的理论底座是：

```text
Go2 locomotion policy 和 X5 teleop arm control 分离；
两者通过 arm state/target observation 只读耦合；
硬件写控制权不交叉。
```

## 1. 先把原系统分成三层

### 第 1 层：硬件执行层

这一层建议尽量不要动。

包括：

- Go2 低层通信
  - `real-wbc/modules/wbc_node.py`
  - `unitree_go.msg.LowState`
  - `unitree_go.msg.LowCmd`
- X5 机械臂通信
  - `arx5-sdk/python`
  - `Arx5JointController("X5", "can0")`

这一层负责：

- 读狗的关节、IMU、足端力
- 读机械臂关节状态
- 把控制命令分别下发到狗和臂

如果你的机器人也是 `Go2-X5`，这一层就是你最应该复用的部分。

### 第 2 层：whole-body controller 层

这一层是他们论文里的核心 RL policy。

它做的是：

- 输入：
  - 狗腿和机械臂的本体状态
  - 机身姿态/角速度
  - 当前末端目标与未来末端目标
  - 上一时刻动作
- 输出：
  - 18 维 whole-body action
    - 前 12 维给狗腿
    - 后 6 维给机械臂

这层对应：

- `real-wbc/modules/wbc_node.py`
  - `lowlevel_state_cb(...)`
  - `policy_timer_callback(...)`
  - `init_policy(...)`

### 第 3 层：任务/策略输入层

这一层不是直接控制电机，而是给 WBC 提供任务目标。

在原系统里，这层可以来自：

- 轨迹回放 pickle
- `run_teleop.py` 发的 `EEF trajectory`
- 未来理论上可接 diffusion / VLA / imitation policy

关键接口：

- 发布当前末端状态：
  - `go2_arx5/eef_state`
- 输入未来末端轨迹：
  - `go2_arx5/eef_traj`

这一层是最容易替换、风险最低的切入点。

## 2. 替换时最重要的判断

你要先决定：你的网络想替换哪一层。

实际有三种路线。

### 路线 A：只替换“上层任务网络”，保留底层 whole-body RL policy

这是最推荐的第一步。

做法：

- 保留 `wbc_node.py`
- 保留 Go2 和 X5 的底层执行链
- 不再用他们的 `run_teleop.py` 或 pickle 轨迹
- 改成你的网络去订阅 `eef_state`
- 你的网络输出未来末端目标轨迹到 `eef_traj`

本质上：

- 你的网络负责“想让末端去哪”
- 他们的 WBC 负责“怎么让狗+臂一起实现”

优点：

- 最安全
- 复用程度最高
- 最少碰底层执行逻辑
- 你不用直接处理腿-臂协调

缺点：

- 你受限于他们这个 WBC 的行为风格
- 你不能完全主导 whole-body 动作分配

### 路线 B：替换 whole-body RL policy，但保留底层执行和状态读取

这是第二步方案。

做法：

- 保留 `wbc_node.py` 里硬件 I/O 那部分
- 替换 `init_policy(...)` 和 `policy_timer_callback(...)` 中的 actor 推理逻辑
- 你的网络直接输出 18 维 whole-body action
- 仍然复用：
  - Go2 的 `lowcmd`
  - X5 的 `arx5-sdk`
  - 现有的安全边界、启动流程、手柄急停

本质上：

- 你保留“执行器适配层”
- 你替换“18 维联合控制策略”

优点：

- 你能完全控制 whole-body policy
- 保留原始硬件通信链和大部分部署框架

缺点：

- 你必须自己保证 18 维动作对真机稳定
- 风险显著高于路线 A
- 你要自己处理腿和臂的耦合

### 路线 C：完全绕过他们的 WBC，自建整套控制链

不推荐一开始这么做。

做法：

- 直接自己管理：
  - Go2 `lowstate/lowcmd`
  - X5 `Arx5JointController`
- 自己做状态拼接、时序同步、控制循环、急停和保护

优点：

- 完全自由

缺点：

- 工作量最大
- 风险最高
- 真机最容易出问题

如果你不是必须彻底重写，没必要先走这条路。

## 3. 对你这个目标，推荐的替换顺序

如果你的最终目的是“替换网络”，但硬件还是 `Go2-X5`，建议按下面顺序推进。

### 第一步：先只替换上层任务网络

先把你的网络接到：

- 输入：`go2_arx5/eef_state`
- 输出：`go2_arx5/eef_traj`

这一步你只需要学习和适配：

- 末端位姿定义
- 时间戳
- 轨迹长度 / 未来预览点
- 夹爪控制

这一步成功的标志是：

- 不改底层 WBC
- 你的网络可以稳定驱动机械臂末端任务

### 第二步：如果上层能力不够，再替换 18 维 whole-body 网络

这时你再动：

- `wbc_node.py` 里的 actor 加载
- obs 构造
- action 输出

但仍保留：

- 手柄启动/急停
- 站立初始化
- Go2 低层消息发送
- X5 SDK 控制

### 第三步：最后才考虑改通信/执行层

只有在这些情况下才值得动：

- 你发现原始控制频率不够
- 你需要不同的动作空间
- 你需要改机械臂或狗腿的控制模式
- 你需要新的安全机制

否则不要一开始碰这层。

## 4. 你最该复用的部分

如果你是要“换网络，不换机器人”，下面这些最该保留。

### 必须尽量保留

- `real-wbc/modules/wbc_node.py` 中的：
  - Go2 `lowstate` 读取
  - Go2 `lowcmd` 下发
  - X5 `get_state()` / `set_joint_cmd()`
  - 手柄控制逻辑
  - 紧急停止
  - 站立初始化
- `real-wbc/modules/common.py`
  - 关节顺序映射 `reorder(...)`
- `arx5-sdk/`
  - 机械臂控制接口

### 可以优先替换

- `go2_arx5/eef_state` -> `go2_arx5/eef_traj` 之间的上层网络
- `wbc_node.py` 中 `self.actor(...)` 的那部分

### 不建议一上来就改

- `LowCmd` 打包逻辑
- CRC
- Go2 底层 DDS/ROS2 链
- X5 CAN 通信逻辑

## 5. 两种最实用的替换接口

### 接口 1：末端轨迹接口

这条接口最重要。

输入给你的网络：

- `EEFState`
  - 当前末端位姿
  - 夹爪状态
  - 时间戳

你的网络输出：

- `EEFTraj`
  - 一串未来末端位姿
  - 夹爪目标
  - 对应 tick

这条路线下，你不用关心腿和臂如何协调。

### 接口 2：18 维联合动作接口

如果你要替 whole-body policy，就直接替换：

- actor 输入：当前 obs
- actor 输出：18 维动作

然后继续走原来的：

- `action_scale + action_offset`
- 前 12 维 -> Go2
- 后 6 维 -> X5

这条路线要求你完全理解：

- obs 组成
- 动作尺度
- 关节顺序
- PD 增益

## 6. 如果你要替 whole-body 网络，必须对齐的 6 件事

### 1. 动作定义要对齐

原系统的 18 维动作不是直接电机电流，而是“归一化后的目标关节位置偏移/目标位置动作”。

你必须对齐：

- `action_scale`
- `action_offset`

否则你的网络输出会直接把真机打飞。

### 2. 关节顺序要对齐

狗腿在策略内部顺序和接口顺序不一样。

要看：

- `real-wbc/modules/common.py`
  - `policy_joint_order`
  - `interface_joint_order`
  - `reorder(...)`

如果不对齐，你会出现：

- 左前腿动作发到右前腿
- 腿和臂维度错位

### 3. 观测定义要对齐

他们的 whole-body policy 输入不是随便拼的，默认包括：

- 18 维关节位置
- 18 维关节速度
- 3 维重力方向
- 3 维角速度
- 末端目标预览
- 上一时刻动作

如果你替换模型但不替换 obs 定义，必须保持严格一致。

### 4. 控制周期要对齐

他们的 policy 频率来自：

- `sim dt * decimation_count`

部署侧按这个频率出动作。

如果你的网络需要不同频率，要么：

- 外面包一层插值/保持器
- 要么修改部署定时逻辑

但不建议第一版就动。

### 5. 启动姿态要对齐

原系统不是一上电就直接跑策略，而是：

- 先站起来
- 再启动 policy

这个流程很关键。

如果你替了网络，也最好保留：

- `R1` 站立
- `L2` 启动策略
- `L1` 急停

### 6. 目标坐标系要对齐

原系统的 reaching 输入默认不是 base frame，而是：

- 末端相对于当前观测末端的局部目标误差

这个逻辑在：

- `wbc_node.py`
  - `local_target_pose = inv(observation_link_pose) @ global_target_pose`

如果你接自己的网络，最容易错的不是模型，而是坐标系。

## 7. 对你来说最稳妥的工程路线

我建议直接这样做：

### 阶段 1

保留原 `wbc_node.py`，只替换上层：

- 你的网络订阅 `eef_state`
- 你的网络发布 `eef_traj`

目标：

- 验证你的网络是否能稳定给出可执行的末端轨迹

### 阶段 2

如果阶段 1 成功，再替换底层 WBC actor：

- 保留硬件读写
- 保留急停、站立、手柄流程
- 只替换 obs -> action 网络

目标：

- 验证你的 whole-body policy 是否能在原执行链上稳定工作

### 阶段 3

最后才考虑重写部署壳层：

- 只在你确认原框架限制了你的网络时才做

---

## 8. 一句话结论

对于你的目标，最合理的方法不是“推倒重来”，而是：

- 把 `Go2-X5` 真机执行链当成稳定底座
- 先替换 `eef_state -> eef_traj` 这一层
- 如果还不够，再替换 `obs -> 18d action` 这一层
- 最后才考虑动底层通信和控制壳

如果你后面要继续推进，下一步最值得做的不是直接改代码，而是先把下面两个接口定死：

- 你的网络到底输出 `EEFTraj`
  还是
- 你的网络直接输出 `18` 维 whole-body action`

这两个方向的工程量和风险差很多。
