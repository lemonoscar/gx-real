# 硬件选择与取舍

这份文档记录 Go2 + X5/ARX5 系统的硬件取舍。它不是上机步骤，而是帮助后续维护时理解为什么当前仓库保留这些硬件依赖。

## 1. Go2 作为移动底盘

优点：

- 成本和重量相对适中。
- SDK、ROS2 消息和低层接口比较容易接入。
- 对当前 `12D leg policy` 部署足够直接。

主要限制：

- 负载能力有限，机械臂会明显增加前腿负担。
- 长时间站立或高增益调试时容易发热。
- 内置 MCF motion mode 和低层 `lowcmd` 不能同时抢控制权。
- 每次上电后的姿态校准会影响低层控制稳定性。

维护建议：

- 上机前先确认 Go2 姿态和自校准状态。
- 跑低层 policy 前用 `MotionSwitcherClient::ReleaseMode()` 释放 MCF。
- 如果关节长期跟不上目标，不要只继续加 Kp；同时检查控制权、力矩限制、电池、关节顺序和站姿 offset。

## 2. X5/ARX5 作为机载机械臂

优点：

- 重量和臂展适合 Go2 这一级别的底盘。
- 可通过 `arx5_interface` 做关节控制。
- 机械臂状态和命令链路相对独立，便于和腿部 policy 解耦。

主要限制：

- 依赖稳定的 24V 供电和 CAN 链路。
- 初始化失败时常见报错是电机未初始化，而不是 Python 代码问题。
- 行走时线缆固定、机械臂目标姿态和底盘稳定性强相关。

当前代码策略：

- 启动时尝试初始化 ARX5。
- 初始化失败默认降级为 body-only，让腿部调试不被机械臂硬件阻塞。
- 需要机械臂强制在线时使用 `--require-arm`。

## 3. iPhone / MoCap 位姿估计

原始 UMI-on-Legs 任务空间控制需要外部位姿估计，用于构造末端目标和机器人基座状态。

当前 `leg12 + arm passthrough` 默认：

```bash
--pose_estimator none
```

因此 iPhone/MoCap 不是当前上机主链路的必需项。

保留这些代码的意义：

- 后续如果恢复任务空间末端轨迹控制，仍可使用 iPhone 或 MoCap。
- MoCap 延迟低、精度高，但不适合野外环境。
- iPhone 更容易部署，但延迟和漂移会明显影响动态控制。

建议：

- 当前先把腿部低层控制和 X5 关节控制跑稳。
- 只有在需要恢复 EEF trajectory 或视觉闭环时，再引入 iPhone/MoCap。

## 4. GoPro 和 UMI 视觉采集

GoPro、采集卡、fin-ray gripper 属于原 UMI 数据采集和模仿学习链路。

优点：

- 轻量，易安装。
- 可用于采集腕部/末端视角数据。

限制：

- 采集卡会引入额外延迟。
- 视觉 SLAM 对光照和纹理敏感。
- 对当前 leg12 行走调试不是必要依赖。

当前建议：

- 当前真机行走调试不要把 GoPro 作为控制闭环依赖。
- 如需恢复 VLA/模仿学习数据采集，再单独整理 GoPro 采集链路。

## 5. 当前优先级

短期维护重点：

1. Go2 低层通信稳定。
2. MCF 释放逻辑可靠且经过 `CheckMode()` 复核。
3. X5 `can0` 和供电可靠。
4. `policy.onnx + env.yaml` 的动作/观测映射清楚。
5. 上机日志足够支持定位腿部和机械臂问题。

暂不优先：

- SpaceMouse teleop。
- GoPro 数据采集。
- iPhone VIO。
- diffusion policy 部署。
